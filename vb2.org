*** Auth flow
1. Frontend uses Google's Identity Services JS library (the "Sign in with Google" button) to get the user to authenticate directly with Google in the browser.
2. Google hands the frontend a signed ID token (a JWT from Google, containing email, name, etc.) — no redirect back-and-forth through your Flask server needed.
3. Frontend POSTs that ID token to your Flask backend (e.g. /auth/google).
4. Backend verifies the token's signature against Google's public keys (via the google-auth Python library's id_token.verify_oauth2_token), extracts the email, looks up or creates a User row.
5. Backend issues its own JWT (via flask-jwt-extended or manually with pyjwt) for subsequent API calls — this is the token your Vue app stores and sends as Authorization: Bearer ... on every request after that.

DUE-COUNTER / TIME-LAPSE MECHANIC - DECIDED
- due_dates: target interval value (grows 1 -> 2 -> 4 -> 8...) set when word
  status changes/graduates
- due_counter: starts at due_dates, decrements toward 0; 0 = due
- Decrement trigger: compare TODAY's calendar date vs book's
  wd_last_practiced/dw_last_practiced (per direction). If today is later
  (not >=24hrs -- literal calendar-day-later), decrement ALL words'
  due_counter for that direction by 1 (floor 0), in one pass at session
  start (instantaneous, few hundred rows). This is the whole point of using
  a counter instead of absolute due-dates: skipping a week only costs -1,
  not -7, avoiding due-pileup.
- Book-level last_practiced (per direction) drives this, NOT per-word --
  deliberately chosen over per-word so untouched words still decay properly
  even if not touched every session.

SYNC / RECONCILIATION ARCHITECTURE - DECIDED
- Reconciliation happens at TWO points, both real:
  1. CLIENT-SIDE: on every load (GET /books/{id}), client compares its
     localStorage copy against server response per field-group timestamp
     (book metadata / word content / word practice-state), keeps newer,
     produces merged local state.
  2. SERVER-SIDE: on /sync (POST), server does lightweight per-field-group
     LWW check against its own stored timestamps before overwriting (NOT
     full reconciliation of two other copies -- just guards against two
     near-simultaneous device syncs clobbering each other). Server returns
     the reconciled result.
  3. Client then reconciles its local copy again against that /sync
     response (closes the loop, symmetric with GET flow).
- Rationale: client-only reconciliation was insufficient because two
  devices syncing near-simultaneously could have one's reconciled write
  clobber the other's, since by definition each device only reconciles
  against what it personally fetched.

LOCAL STORAGE STRATEGY - DECIDED
- Path 1 chosen explicitly: NOT building offline-mode. Server round-trip
  still happens on every "list books" / "load book" action.
- localStorage holds ONE book at a time (words + practice-state, both
  directions) -- NOT the book list (book list always fetched fresh from
  server, cheap/rarely changes).
- Local (Pinia, backed by localStorage) is authoritative only WITHIN a
  session, between load points -- exists specifically to survive page
  reload without losing in-progress practice progress (Pinia state alone
  is memory-only, wiped on reload).
- Written to localStorage after every card-answer event (cheap/instant,
  full-book JSON, no granular per-word writes -- consistent with
  whole-book-not-deltas design already used for server sync).
- Switching to a different book or direction session: sync current book to
  server FIRST (blocking), only then clear localStorage and load the new
  book. If sync fails, block the switch entirely -- switching requires
  fetching the new book's data anyway, so this isn't an extra guard, it's
  inherent to the flow.

*** Data structure and logic
**** data structure (will use index, not ID)
- const lw = ref<number>[]([]) // learning window
- const ww = ref<number>[]([]) // waiting window
- wordsNoPrac: int[]  // words without practice (for the direction)
- lastSyncTime: DateTime

**** overall flow
- sync with server
- decrement due counters (0 or -1)
- create wordsNoPrac
- fill lw and ww
- (practice)
- (if +1 day, sync with server)
- on leaving practice, sync with server

**** Filling lw and ww (for the direction)
- if lw.length > 5 -> move to ww
- if ww.length > 5 -> remove from ww
- for steps below, if lw.length == ww.length == 5 -> quit
- search prac with status 'review' and due_cnt == 0
- put to lw -> ww
- if lw.length < 5, move from ww until (lw.length == 5 or ww.length == 0)
- search prac with status 'learning'
- put to lw -> ww
- search prac with status 'waiting'
- put to lw -> ww
- search prac with status 'new'
- put to lw -> ww
- from wordsNoPrac, create practice with 'new'
- put to lw -> ww

**** Practice
- check if lastSyncTime > 1 day then sync with server
- fill lw and ww
- remove one at head of lw
  - once more -> put at tail of lw
  - ok
    - status == new | learning -> status = waiting, put at tail of ww
    - status == waiting -> status = review, init due_dates/counter
    - status == review -> put at tail of ww
  - memorized
    - status == review -> due_dates x 2, dut_cnt = due_dates
    - status others -> status = review, due_dates = dut_cnt = 1
- loop from top
